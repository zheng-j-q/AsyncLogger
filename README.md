# Linux 异步日志智能运维 Agent（AsyncLogger）

把异步日志系统的部署与排障经验，拆成**可判定的步骤和分级的工具**：能自动做的只到「看」和「验」，会改变线上状态的动作一律留给人。

> 产品定义与验收口径：[PRD.md](PRD.md)
> 个人项目｜独立设计与开发｜2026.07 - 2026.08｜B 端 AI 产品作品集之一
> 另两个项目：[MemoryPool](https://github.com/zheng-j-q/MemoryPool) · [SalesDataTool](https://github.com/zheng-j-q/SalesDataTool)

## 这个仓库里有什么

| 层 | 内容 | 状态 |
|---|---|---|
| 底层内核 | Linux 高并发异步日志系统（epoll ET、双线程解耦、自定义粘包协议）及测试 | **已开源，可编译运行** |
| Agent 产品层 | 排障 SOP、工具权限分级、闭环状态机、异常中止与回滚、验收口径 | **设计定义见 [PRD](PRD.md)** |

## 解决什么问题

异步日志系统部署到嵌入式设备时，要手动调 epoll 边缘触发行为、刷盘阈值等底层参数；线上出现阻塞、丢包，定位依赖熟悉这套内核的人。部署耗时原为 4 小时，产品目标 20 分钟。

但真正难的不是「有没有工具」，而是**专家脑子里那套排障顺序没被写下来**：先看什么、看到什么算异常、异常之后能自动做哪一步、哪一步必须停下来叫人。

## 产品判断：按动作后果分级，不按技术难度分级

| 档 | 动作 | 是否自动 | 理由 |
|---|---|---|---|
| L0 | 查看配置、读取队列与压测记录 | 自动 | 不改变系统状态 |
| L1 | 启动压测、采集指标 | 自动 | 可重复、可回滚 |
| L2 | 生成配置建议、生成归因报告 | 可生成、**不可应用** | 产出物，不是线上动作 |
| L3 | 动态调参、服务启停 | **禁止自动执行** | 改变线上状态，误操作代价高 |
| L4 | 中止闭环、回滚配置 | 自动 | 安全方向的操作 |

配套的排障 SOP 把「现象 → 检查项 → 判定依据 → 允许动作」写成表格（见 [PRD 第 3 节](PRD.md)）。例如：队列持续堆积且写盘速率偏低时，允许只读采集并给出归因建议；需要重启服务验证且存在在途日志时，必须暂停并提示人工确认。

**这条边界是本项目最重要的产品判断**——它和「把大模型接进运维脚本」的区别，不在于用了什么模型，而在于哪些动作被允许自动化。

## 闭环与异常分支

```text
部署场景输入 → 槽位校验（缺则反问）→ 检索知识库 → 生成配置建议
→ 人工确认 → 应用配置 → 一键压测 → 采集指标
→ 异常？ 是 → 归因报告 + 中止 / 回滚
        否 → 输出部署结论与配置快照
```

压测出现崩溃、死锁或数据丢失时闭环**中止**，而不是继续往下跑；未完成的配置变更回滚到上一版快照。

## 效果与口径

| 指标 | 变化 | 说明 |
|---|---|---|
| 部署周期 | 4 小时 → 20 分钟 | 从场景输入到完成部署验证；统计口径见 [PRD 第 7 节](PRD.md) |

异常处理能力、日志吞吐等数值涉及评测集与硬件环境，统一放在 PRD 的「指标定义与验收口径」中说明口径后再对外引用。其中**单服务端日志吞吐属于底层内核能力，不是 Agent 带来的收益**，两者不合并计算。

## 运行与验证

环境：Linux / WSL2 / macOS，g++ 7.0+，CMake 3.10+。

```bash
git clone https://github.com/zheng-j-q/AsyncLogger.git
cd AsyncLogger
mkdir build && cd build
cmake ..
make
./async_logger
cat logs/app.log
```

预期输出：日志系统初始化成功、SocketServer 监听端口 8888、收到连接与消息、心跳显示队列大小。

测试覆盖：epoll 并发连接接收、粘包拆包协议解析、异步队列前端不阻塞、日志按大小滚动、24 小时压测无崩溃无死锁、Valgrind 内存泄漏检测。
